## 008 — Accounts and data (2026-11-27)

- Auth: email magic link only (no passwords). Google is optional and deferred: it cannot supply a birth year.
- Age gate in three layers: form (year + 16+ checkbox), then a DB trigger on `auth.users` that rejects
  sign-up without a birth year giving 16+, plus a `check` on `profiles.birth_year`. Coarse by design (year only).
- RLS on every table; `anon` has no grants. `consents` is append-only for the user.
- Account deletion is a `security definer` SQL function (`delete_my_account`), so no service-role key
  ever exists in the web app. Export is a JSON download built through RLS-filtered selects.
- Protected area is `/cuenta/*`; sign-in is `/entrar`. Middleware runs only on `/cuenta/*`.
- Consent records store legal text versions (`LEGAL_VERSIONS`, placeholder until WS-D publishes texts).

## ADR-001: Rust engine, TypeScript face (2026-11-27)

Owner asked for Rust wherever reasonable. Data logic (collectors, classification, matching, alerts,
case scoring) moves to a Cargo workspace; the site stays Next.js + MDX on Vercel; no server of our
own; the CV is processed in the browser via WebAssembly. Full rationale: `docs/architecture.md`.

## ADR-002: Postings are written through PostgREST, not `sqlx` (2026-11-27)

Context: the Rust pipeline must upsert into Supabase Postgres from GitHub Actions. The brief allowed
either `sqlx` with `DATABASE_URL`, or PostgREST with `SUPABASE_URL` + `SUPABASE_SERVICE_ROLE_KEY`.

Decision: PostgREST over HTTPS (`reqwest`), as the Python version did.

Why: (1) those two secrets already exist for the workflow and the keep-alive job, so no new secret has
to be created; (2) Supabase's direct database host is IPv6-only on the free tier and GitHub-hosted
runners are IPv4, so `sqlx` would need the pooler URL and its transaction-mode quirks; (3) a much
smaller dependency tree and faster release builds; (4) the writes are two simple statements (an
upsert on `source,external_id` and an expiry `PATCH`), which PostgREST covers fully. The cost is that
we do not get compile-time-checked SQL, which `sqlx` runtime queries would not give us either.
Revisit when a job needs real transactions or complex queries (probably `cw-alerts`).

## ADR-003: Rust engine layout and tooling (2026-11-27)

- Workspace `crates/`: `cw-domain` (types), `cw-sources` (API clients and their terms),
  `cw-classify` (YAML rules), `cw-pipeline` (CLI). `cw-match`, `cw-wasm`, `cw-alerts` are phase 2.
- Rules and employers live in `config/` (`rules.yaml`, `companies.yaml`) and are embedded in the
  binary with `include_str!`; `--config-dir` overrides them without recompiling.
- TypeScript types are generated by `ts-rs` into `src/lib/generated/` on `cargo test`
  (`.cargo/config.toml` sets `TS_RS_EXPORT_DIR`). CI fails if the committed copies are stale.
  Prettier ignores that folder and `crates/` (generated and golden data).
- TLS: `reqwest` with `rustls-no-provider` plus the `ring` provider installed at start-up. The default
  provider (`aws-lc-rs`) needs cmake and NASM to build on Windows; `ring` only needs a C compiler.
- Parity: `crates/cw-pipeline/tests/golden/` holds the output of the Python pipeline (recorded fixtures
  plus 605 synthetic cases) and the Rust code must reproduce it exactly. The Python pipeline was
  deleted after that test passed; the golden files stay as regression data for the rules.
- Local Windows builds need a C toolchain: MSVC Build Tools, or MinGW-w64 with
  `cargo +stable-x86_64-pc-windows-gnu`. `rust-toolchain.toml` stays on plain `stable` so CI on Linux works.
